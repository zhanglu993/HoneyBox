# eBadge BLE 投屏吞吐与设备复位实测报告

面向固件同事。本文只记录实测数据，不含推测；每项结论都注明了取数方式。

- 日期：2026-08-06
- 设备：eBadge `03:22:33:77:33:13`
- 应用：HoneyBox，分支 `codex/windows-media-parity`
- 主机：Windows 11 26100（Release 构建）／Android V2405A（Release 构建）

---

## 摘要

1. **BLE 链路速度在 Windows 与 Android 上完全一致**，两端 MTU 均为 247、
   分片 231 字节、单包往返约 62ms。此前"Windows 蓝牙更慢"的判断经实测否定。
2. **设备的可持续接收速率约 60 kbps。** 超过之后信用窗口先被打到 0，随后
   固件复位、BLE 链路断开。
3. **信用机制没有起到保护作用。** 应用全程严格遵守信用窗口，信用值从未透支，
   设备仍然复位。这是本报告希望固件侧重点确认的问题。
4. Android 上同样存在偶发复位（由使用方观察到），说明该问题**不是 Windows
   特有**，只是 Windows 侧发包更密集，把它稳定触发了。

---

## 一、链路能力：两端一致

为排除平台差异，让两端跑**完全相同的代码路径**（流通道改用带确认写入，
即每包等待 ATT 确认），连接同一台 eBadge，对比单包往返耗时。

| 项目 | Windows | Android |
| --- | --- | --- |
| 协商 ATT MTU | 247 | 247 |
| KS_FRAME 分片 | 231 字节 | 231 字节 |
| 单包往返（均值） | 62.0 ms | 61.1 – 65.5 ms |
| 单包往返（峰值） | 92.1 ms | 88.7 – 95.4 ms |
| 折算吞吐 | 31 kbps | 29 – 32 kbps |

取数方式：应用在流写入路径上按每 50 次写入统计一次墙钟耗时。写队列是严格
串行的，因此单次写入耗时即链路的单包成本。

**结论：两端链路速度没有差别。** 约 62ms 的往返意味着连接间隔约 60ms，
与 Windows 默认的 Balanced 档（30–60ms）一致；Android 未主动请求高优先级
连接参数，实测也落在同一区间。

补充：Windows 侧曾尝试通过 `BluetoothLEDevice.RequestPreferredConnectionParameters`
请求 `ThroughputOptimized`（固定 15ms 间隔），请求被系统接受但**链路参数
没有任何变化**（62.0ms → 62.0ms）。结合 Android 同为 60ms，可判断连接间隔
由设备端决定。

## 二、速率扫描：复位阈值

固定其余条件，仅改变应用侧的发送节流速率，每档约 20 秒。
流配置：H.264 / 368×368 / 15 fps / 编码器码率 150 kbps；
会话开启时设备给出初始信用 64，之后每次 `KS_CREDIT` 补 4。

| 节流速率 | 包间隔 | 已发帧 | 发送失败 | 信用耗尽 | 信用超时 | CREDIT 次数 | 平均帧率 | 链路断开 |
| --- | --- | --- | --- | --- | --- | --- | --- | --- |
| **60 kbps** | 32.9 ms | 70 | 0 | **0** | **0** | 134 | 3.5 fps | **无** |
| 90 kbps | 22.0 ms | 111 | 2 | 3 | 3 | 202 | 2.9 fps | 1 次 |
| 120 kbps | 16.5 ms | 17 | 6 | 8 | 8 | 28 | 0.5 fps | 2 次 |
| 160 kbps | 12.4 ms | 9 | 3 | 4 | 4 | 14 | — | 未记录 |

> 160 kbps 那次的构建尚未加入断链日志，故"链路断开"一栏无数据，不代表未断开。

### 60 kbps：健康状态

信用值在 58–62 之间稳定波动，形成收发平衡：

```
信用=60 信用=59 信用=59 信用=58 信用=61 信用=60 信用=61 信用=60 信用=61 信用=60
信用=61 信用=60 信用=62 信用=61 信用=62 信用=61 信用=59 信用=62 信用=60 信用=59
```

全程 0 次信用耗尽、0 次发送失败、0 次链路断开。

### 90 kbps：耗尽后复位

信用被逐步打到 0，连续三次等待补充，随后链路断开：

```
流/已发 P 1888B · 累计=8 信用=0
流/信用耗尽 seq=8  off=0/2451 等待补充...
流/信用耗尽 seq=9  off=0/2322 等待补充...
流/信用耗尽 seq=10 off=0/2268 等待补充...
BleManager: link dropped after 205 FFC5 notifications
```

### 120 kbps：快速复位

仅 15 个 FFC5 通知后即断开，重连后再次断开：

```
BleManager: link dropped after 15 FFC5 notifications
（自动重连）
BleManager: link dropped after 15 FFC5 notifications
```

**结论：设备的可持续接收速率在 60 kbps 附近。** 60 与 90 之间是分界；
90 kbps 能撑约 20 秒后复位，120 kbps 数秒内即复位。

## 三、希望固件侧确认的问题

### 问题 1：过载时复位，而非依靠信用窗口反压

这是本报告的核心。

- 应用**全程严格遵守信用窗口**：每发一个 KS_FRAME 分片扣减一个信用，
  信用为 0 时停止发送并等待 `KS_CREDIT`。日志中信用值从未出现负数。
- 即便如此，只要发送速率超过约 60 kbps，设备仍会先出现信用长时间不补，
  最终复位。

**期望行为**：设备缓冲不足时应停止发放信用，让发送方自然阻塞等待，
而不是复位。信用机制本身已经具备这个能力。

**可能方向**（供参考，非结论）：初始信用 64 与每次补 4 的窗口大小，
是否与实际接收缓冲容量匹配？64 个信用对应约 64 × 231 ≈ 14.4 KB，
若实际缓冲小于此值，发送方在完全合规的前提下也会撑爆设备。

### 问题 2：Android 上同样存在偶发复位

由使用方观察到，Android 正常使用中设备也会时不时重启。本报告的扫描数据
提供了稳定复现路径，可用于定位。

### 问题 3：复位后的行为

120 kbps 档下观察到设备复位 → BLE 断开 → 应用自动重连 → 再次复位的循环。
如果固件在复位后能保留或上报异常原因（如缓冲溢出计数），会显著加快定位。

## 四、复现步骤

1. 取分支 `codex/windows-media-parity`，构建 Windows Release：
   ```
   flutter build windows --release
   ```
2. 用附带的脚本以指定速率启动（脚本位于构建产物目录）：
   ```
   .\run-paced.ps1 120000     # 单位 bps；0 表示关闭限速
   ```
   该速率通过环境变量 `HONEYBOX_STREAM_PACING_BPS` 传入，无需重新构建。
3. 连接 eBadge → 进入摄像头页 → 保持默认 H.264 / 368×368 / 15 fps / 150 kbps
   → 开始投屏。
4. 观察日志中的以下行：
   ```
   BleManager: mtu=... streamChunk=... pacing=...ms@...bps
   BleManager: stream write writes=50 ... mean=..ms -> .. kbps
   BleManager: FFC5 #N len=.. key=0x..
   BleManager: link dropped after N FFC5 notifications
   流/CREDIT +4 -> 剩余=..
   流/信用耗尽 / 流/信用超时
   ```

**注意**：设备一旦复位过，后续测试结果可能不可信 —— 我们曾在同一档位
（60 kbps）先后得到"全线失败"和"完美跑通"两种结果，差别仅在设备状态。
**每次换档前请先重启设备。**

## 五、应用侧已做的处理

在固件问题解决前，应用侧按实测阈值做了限速缓解：

- 非 Android 平台按目标码率给流写入加最小间隔，默认 **60 kbps**
  （`lib/services/ble_write_pacer.dart`）。
- 该值可由 `HONEYBOX_STREAM_PACING_BPS` 运行时覆盖，便于继续标定。
- Android 不受影响：其协议栈会阻塞每次无确认写入直到控制器有空间，
  自带背压；Windows 约 1.5ms 就返回，需要应用自己限速。

**代价**：60 kbps 对约 1.6 KB 的 H.264 帧只能支撑约 3.5 fps，
远低于配置的 15 fps。要提升帧率，要么固件侧提高可持续接收能力，
要么应用侧降低编码码率与分辨率以换取更高帧率。
